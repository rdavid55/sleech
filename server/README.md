# Запуск кабинетов СЛИЧ

Источник разработки — **https://github.com/rdavid55/sleech**. Старый Sites-проект не используется и не является API кабинета.

## Что работает на GitHub Pages

Страницы, опрос, подбор услуги, плановые сметы, учебные инструменты и скачивание описания. GitHub Pages публикует статические файлы и не исполняет `server/`. Поэтому серверная часть и база не начинают работать от одного коммита.

В `docs/assets/portal-config.js` намеренно нет выдуманного адреса. Пока `apiBase` пуст на GitHub Pages, кабинет явно сообщает, что приём заявок не подключён. Сайт не выводит фиктивный номер, не сообщает об успешной отправке и не передаёт данные в старый Sites.

## Полная система локально

Требуется Node.js 24 или новее. Зависимостей npm нет.

```bash
npm test
npm start
```

Откройте http://localhost:8080. Этот сервер одновременно отдаёт `docs/` и `/api/`; `apiBase` оставьте пустым. База создаётся в `data/slich.sqlite`. Файлы вложений хранятся внутри этой базы. Каталог `data/` не публикуется сервером и исключён из Git.

Посетитель регистрируется как представитель новой организации. Имя организации не является идентификатором: даже две компании с одинаковым названием получают разные UUID. Для доступа коллеги создаётся одноразовая ссылка-приглашение из кабинета компании. Поиск совпадающего названия не объединяет организации.

## Учётные записи команды

Только администратор сервера может создавать команду. Сайт не содержит общего пароля, списка разрешённых e-mail или переключателя, выдающего роль сотрудника.

Для Bash скрыто введите отдельный новый пароль для каждого участника (от 12 символов):

```bash
read -rs -p 'Новый пароль: ' slich_password
printf '\n'
printf '%s' "$slich_password" | npm run team -- add team-admin 'Администратор' admin
unset slich_password

read -rs -p 'Новый пароль: ' slich_password
printf '\n'
printf '%s' "$slich_password" | npm run team -- add team-engineer 'Инженер' operator
unset slich_password
```

Пароль проходит через stdin, не аргумент команды и не Git. В базе хранится scrypt-хеш с индивидуальной солью. Создание команды не создаёт платную услугу и не привлекает метролога автоматически.

Для сброса пароля используйте `npm run team -- reset-password <login>` с новым паролем через stdin. Существующие сеансы пользователя будут отозваны. Самостоятельного восстановления по e-mail нет: почтовый сервис не подключён.

## Сервер в интернете

Нужны сервер с постоянным диском, домен, HTTPS и доступ к размещению. Эти реквизиты и доступы не хранятся в репозитории. На GitHub Pages сервер запустить нельзя.

Вариант с Docker Compose:

1. Клонировать репозиторий на выбранный сервер. Установить Docker с Compose.
2. Направить DNS домена кабинета на сервер; обеспечить доступ к портам 80 и 443. Если на сервере уже есть веб-сервер, подключить приложение к нему вместо конкурирующего сервиса `https`.
3. Скопировать `.env.example` в `.env`, задать свой `SLICH_DOMAIN` и точные разрешённые origin в `ALLOWED_ORIGINS`. Origin GitHub Pages — `https://rdavid55.github.io`, без пути `/sleech`. Доступ из других origin отклоняется.
4. Запустить `docker compose up -d --build`. Именованный том `slich-data` сохраняет SQLite и вложения при пересборке контейнеров. **Не выполнять `docker compose down -v` для обновления:** этот флаг удаляет тома.
5. Проверить `https://<домен>/api/health`: ожидается `service: slich`, `storage: ready`.
6. Создать командные учётные записи. В примерах выше заменить `npm run team -- ...` на `docker compose exec -T server npm run team -- ...`, сохранив передачу пароля через stdin.
7. Задать в `docs/assets/portal-config.js` `apiBase: 'https://<домен>'`, сохранить в GitHub и дождаться обновления Pages. URL не должен содержать `/api`: клиент добавляет его сам. Это публичный адрес, не секрет.
8. Пройти контрольный сценарий ниже. Только после него считать приём заявок подключённым.

Можно разместить весь сайт на этом сервере из того же GitHub-репозитория: тогда `apiBase` остаётся пустым. Публичные Pages при этом можно сохранить для знакомства с проектом.

Сеанс использует `Authorization: Bearer`, а не сторонние cookies, поэтому раздельные origin Pages и API поддерживаются. Ключ хранится в `sessionStorage` вкладки максимум 12 часов; выход отзывает сеанс. Доступ назначается на сервере по организации, не по переданным клиентом `orgId` или `role`.

Прототип ограничивает попытки входа, регистрацию, изменения и отправки. За reverse proxy IP-лимит применяется к адресу прокси; для большого количества посетителей нужен доверенный ограничитель на уровне прокси и отдельный эксплуатационный расчёт.

## Контроль перед реальными заявками

1. Создать две тестовые компании и отправить по заявке.
2. Проверить, что вторая компания не может открыть заявку, сообщение или файл первой даже по прямому ID.
3. Войти командой, увидеть обе заявки, назначить ответственного и подготовить состав работ, результат и цену.
4. Согласовать объём из кабинета соответствующей компании. Убедиться, что изменение цены аннулирует согласование.
5. Перевести согласованную заявку в работу, приложить результат и завершить.
6. Перезапустить сервер и проверить сохранность данных.
7. Создать резервную копию и восстановить её в отдельном окружении.

Командный кабинет — реестр с ручным обновлением списка; e-mail, Telegram, push и круглосуточный мониторинг не подключены. Заявка сохраняется независимо от уведомлений. Для совместной работы нужно выдавать отдельную учётную запись каждому участнику, не передавать общий пароль.

## Резервное копирование и восстановление

```bash
npm run backup -- /secure-backups/slich.sqlite
```

Копия включает SQLite, вложения, историю и учётные записи. Резервное копирование использует SQLite Online Backup API и учитывает WAL; копирование только основного файла работающей базы недостаточно. Каталог копий должен быть вне публичного `docs/`, с ограниченным доступом. Частоту, хранение вне сервера и срок хранения определяет ответственный за эксплуатацию.

Для Docker можно выполнить `docker compose exec -T server npm run backup -- /app/data/backup.sqlite`, затем безопасно скопировать копию с сервера. Хранение копии только в том же томе не защищает от потери сервера.

Восстановление: остановить приложение, сохранить текущую базу отдельно, установить проверенную копию как `data/slich.sqlite` (с правильным владельцем и правами), удалить старые соответствующие WAL/SHM только при остановленном приложении, проверить `PRAGMA integrity_check`, отозвать сеансы запросом `DELETE FROM sessions`, затем запустить приложение и пройти контрольный сценарий.
